# STATUS.md

**Last updated:** 2026-09-21

## Where this stands right now

A real Pi 3B+ is now provisioned and running this project's software end-to-end for the first time. `deploy.sh`/`install.sh` were dry-run against it (a real gap was found and worked around, not yet fixed at the root — see Known gaps), and a genuine WAV chunk was captured from a real RTL-SDR Blog V4 for the first time, validating `build_rtl_fm_cmd()` against real hardware.
That same session surfaced a real architectural gap — `GpsClock` was never actually wired into `hsd.py`, so chunk timestamps relied on the Pi's own RTC-less (and, in practice, wrong) system clock — which is now fixed: `CaptureWorker` takes a pluggable time source, and `hsd.py` runs a `GpsClock` for the daemon's whole lifetime, falling back to system time only when `gpsd` is unreachable or hasn't got a fix yet.
GPS hardware itself is fully validated (see Track B-GPS, done). The Pi has since gotten a real 3D fix outdoors too, and a real 20m FT8 session there decoded 447 genuine over-the-air messages — but that same session found a real bug in `decode_worker.py` (every `ft8_lib`-decoded spot stamped at midnight), now fixed.
Most recently: moved the RTL-SDR + antenna to the dev Mac for faster iteration, and found a **second, more consequential bug** — `rtl_fm` itself intermittently hard-clips its demodulated audio output even when the raw RF/ADC signal is completely clean and stable (proven via a from-scratch reference demodulator that decoded 152 real messages from the same raw I/Q data `rtl_fm` mostly failed on). See `hardware/20260920_rtl_fm_demod_bug.md` for the full investigation — this is likely the dominant reason decode yield has been inconsistent, more so than antenna/band conditions.
The remaining work before a reliable live station is resolving that `rtl_fm` bug (try `-F 9`/`-E dc` first; a custom-demod replacement is the bigger fallback option) and an HF antenna permanently in place at the Pi's deployment location.

Fixed: `CaptureWorker` now takes an optional `now_fn` time-source callable (defaults to system time, unchanged for existing callers/tests); `hsd.py` starts a `GpsClock` for the daemon's whole lifetime in `main()` and feeds `_now_utc()` (GPS-disciplined when available, system-time fallback if `gpsd` is unreachable at startup or hasn't got a fix yet) into `CaptureWorker`. Validated on the real Pi: `_start_gps_clock()` successfully connects to the real `gpsd` instance there, and `_now_utc()` correctly falls back to system time given no fix yet — the code path is live and correct, timestamps will self-correct automatically once a real fix lands. 5 new tests added (4 in `test_hsd.py`, 1 in `test_capture_worker.py` proving `now_fn` is actually honored, not just accepted) — 43 passing total.
- [x] `hsd` OpenRC boot-crash fixed (2026-09-11): found via the dry run above — `logs/`/`chunks/`/`sessions/`/`var/` are gitignored and were never created by `deploy.sh`'s rsync, but OpenRC's `output_log` redirection needs the directory to pre-exist, so the service crashed before `hsd.py` ever ran. `install.sh` now `mkdir -p`s all four.
- [x] First real over-the-air FT8 decode, on the Pi (2026-09-11): with a real GPS fix acquired outdoors and a proper HF antenna connected, a 20m FT8 session (`14.074M`, `ft8_lib`) decoded **447 genuine messages** from real stations worldwide (Europe, Africa, the Americas) — first real proof the whole pipeline works end-to-end. Real gap found by inspecting the session log: `decode_ft8` (`ft8_lib`) always hardcodes `"000000"` as its own reported time-of-day, and `decode_worker.py` blindly trusted that field, so every `ft8_lib`-decoded spot was silently stamped at midnight regardless of when it was actually heard. Fixed: `decode_chunk()` now overrides every spot's `utc_timestamp` with `chunk_start()` (parsed from the chunk filename, which is authoritative — one chunk is always exactly one decode window) instead of trusting the decoder's self-reported time-of-day. Verified on the Pi against real captured chunks. Also added `tools/watch_decodes.py` (live decode monitor, groups output by decode window with a UTC-time + grid-square header) and `hardware/20260911_wifi_field_ops.md` (WiFi-AP connection instructions) for field use without the direct-cable Ethernet link.
- [x] Root-caused a second, likely more consequential decode-yield bug — this time in `rtl_fm` itself, not the antenna/band/RF chain (2026-09-20/21): moved the RTL-SDR + antenna to the dev Mac for faster iteration. A raw-I/Q gain sweep confirmed the ADC/tuner front end is clean up to ~42-43 dB (well above what caused saturation on the Pi at the same nominal gain, confirming that earlier issue was environmental, not this gain value). But a real decode test at that gain showed wildly inconsistent yield (0 decodes, then a lucky 90-second burst of 84, then 0 again) — traced to `rtl_fm`'s own demodulated *audio* output intermittently hard-clipping at the exact 16-bit ceiling, while a dedicated 120-second raw-I/Q capture over the same span proved the underlying RF signal stayed completely clean and stable throughout (0% clipping, steady power, every 15s block). Built an independent reference USB demodulator (`tools/reference_usb_demod.py`, numpy/scipy) against that same saved raw I/Q — it decoded **152 real messages, zero clipping, from all 8 chunks** — conclusively proving the bug is `rtl_fm`'s own processing, not the hardware, antenna, or band. Full writeup: `hardware/20260920_rtl_fm_demod_bug.md`. **This is likely the dominant explanation for inconsistent decode yield so far, more so than band conditions.**

## Known gaps / open questions

- `rtl_fm`'s intermittent audio-clipping bug (see above) — open, not yet fixed.
- `deploy.sh` assumes `rsync` is present on the remote Pi; it isn't shipped by minimal Alpine and isn't vendored into the offline bundle. Fix at the root next time: either vendor `rsync` into `provisioning/build-bundle.sh`'s package list, or make `deploy.sh` fall back to `tar`-over-SSH when `rsync` isn't found remotely.
- `gpsd-clients` (the standard `cgps`/`gpsmon`/`gpspipe` tools) isn't vendored into the offline bundle either — checked via `pkgs.alpinelinux.org`: only ~3.1MiB, and its only dependency (`libncursesw`) is already pulled in transitively by `python3`, so this is a cheap addition for the next bundle rebuild. Without it, watching satellite counts on the Pi needs a raw `socket`+`json` script against `gpsd`'s own protocol instead of a real CLI tool.
- `wsprd` is invoked without `-f` (no dial frequency), so its frequency field is baseband-relative Hz, consistent with `jt9`/`decode_ft8` — absolute RF frequency (dial + offset) isn't computed anywhere yet.
- No cleanup/retention policy for processed WAV chunks in `chunks/` yet — they accumulate on disk indefinitely.
- `jt9`/`wsprd` (the WSJT-X decoder) are still broken on the Pi specifically — missing runtime shared libraries (`libfftw3f`, `Qt5Core`, `libgfortran`, `libgomp`) never vendored into the offline bundle (only their `-dev` build-time packages were). `ft8_lib`/`decode_ft8` works fine on the Pi and is what all real testing so far has used.
