# STATUS.md

**Last updated:** 2026-09-26

## Where this stands right now

A real Pi 3B+ is now provisioned and running this project's software end-to-end for the first time. `deploy.sh`/`install.sh` were dry-run against it (a real gap was found and worked around, not yet fixed at the root — see Known gaps), and a genuine WAV chunk was captured from a real RTL-SDR Blog V4 for the first time, validating `build_rtl_fm_cmd()` against real hardware.
That same session surfaced a real architectural gap — `GpsClock` was never actually wired into `hsd.py`, so chunk timestamps relied on the Pi's own RTC-less (and, in practice, wrong) system clock — which is now fixed: `CaptureWorker` takes a pluggable time source, and `hsd.py` runs a `GpsClock` for the daemon's whole lifetime, falling back to system time only when `gpsd` is unreachable or hasn't got a fix yet.
GPS hardware itself is fully validated (see Track B-GPS, done). The Pi has since gotten a real 3D fix outdoors too, and a real 20m FT8 session there decoded 447 genuine over-the-air messages — but that same session found a real bug in `decode_worker.py` (every `ft8_lib`-decoded spot stamped at midnight), now fixed.
A follow-up session (moved the RTL-SDR + antenna to the dev Mac for faster iteration) found a **second, more consequential bug**: `rtl_fm` itself intermittently hard-clips its demodulated audio output even when the raw RF/ADC signal is completely clean and stable. See `hardware/20260920_rtl_fm_demod_bug.md` for the full investigation. Fixed in code by replacing `rtl_fm` with an `rtl_sdr | csdr` pipeline (`vendor/csdr`, newly vendored), validated against a saved real I/Q capture.
**That fix has now been live-tested against a real antenna for the first time (2026-09-25/26), and it works** — a real 20m FT8 session decoded genuine traffic continuously, every single cycle, a qualitative improvement over `rtl_fm`'s old all-or-nothing behavior. That same live-test session also surfaced and fixed two more real bugs (full writeup: `hardware/20260925_live_capture_and_gps_flakiness.md`): `csdr`'s own shared library wasn't being deployed alongside its executable (fixed in `bin/_platform.sh` + `build-bundle.sh`), and `DecodeWorker` was silently re-decoding the *entire* accumulated backlog of stale WAV files every time a session starts (fixed — it now only reacts to files that arrive after it starts). The GPS "no fix" issue open since 2026-09-11 is also resolved: root cause was the GPS unit's USB connection dropping and re-enumerating to a different device node while `gpsd` kept pointing at the old one — not a code bug. Once pointed at the right device, `hsd`'s `GpsClock` picked up a real fix immediately and chunk timestamps are now genuinely correct end-to-end for the first time.
The remaining work before a reliable live station is getting an HF antenna permanently in place at the Pi's deployment location and running the Phase 1 sustained-capture exit criterion.

Real gap found by inspecting the session log: `decode_ft8` (`ft8_lib`) always hardcodes `"000000"` as its own reported time-of-day, and `decode_worker.py` blindly trusted that field, so every `ft8_lib`-decoded spot was silently stamped at midnight regardless of when it was actually heard. Fixed: `decode_chunk()` now overrides every spot's `utc_timestamp` with `chunk_start()` (parsed from the chunk filename, which is authoritative — one chunk is always exactly one decode window) instead of trusting the decoder's self-reported time-of-day. Verified on the Pi against real captured chunks. Built an independent reference USB demodulator (`tools/reference_usb_demod.py`, numpy/scipy) against that same saved raw I/Q — it decoded **152 real messages, zero clipping, from all 8 chunks** — conclusively proving the bug is `rtl_fm`'s own processing, not the hardware, antenna, or band. Full writeup: `hardware/20260920_rtl_fm_demod_bug.md`.

Confirmed the real cross-built `linux-aarch64` binary against the same saved 120s raw I/Q capture: **133 real messages decoded cleanly across all 7 chunks, zero clipping** — matching the earlier Python reference demod's result. Wired in for real: `capture_worker.build_csdr_capture_cmd()` builds an `rtl_sdr | csdr convert | csdr fractionaldecimator | csdr bandpass | csdr realpart | csdr limit | csdr convert` pipeline (csdr's own documented "modified Weaver demodulator" USB recipe), `CaptureWorker` now supports shell-pipeline `capture_cmd` (a `str`, run with `shell=True` in its own process group so `stop()` can tear down every stage together, not just the shell — a real termination bug that would otherwise orphan `rtl_sdr`/`csdr` processes), and `hsd.py`'s `start_listening()` uses the new builder by default. `build_rtl_fm_cmd()` is kept for reference, not deleted. Full writeup: `hardware/20260925_live_capture_and_gps_flakiness.md`.

## Known gaps / open questions

- `deploy.sh` assumes `rsync` is present on the remote Pi; it isn't shipped by minimal Alpine and isn't vendored into the offline bundle. Fix at the root next time: either vendor `rsync` into `provisioning/build-bundle.sh`'s package list, or make `deploy.sh` fall back to `tar`-over-SSH when `rsync` isn't found remotely.
- `gpsd-clients` (the standard `cgps`/`gpsmon`/`gpspipe` tools) isn't vendored into the offline bundle either — checked via `pkgs.alpinelinux.org`: only ~3.1MiB, and its only dependency (`libncursesw`) is already pulled in transitively by `python3`, so this is a cheap addition for the next bundle rebuild. Without it, watching satellite counts on the Pi needs a raw `socket`+`json` script against `gpsd`'s own protocol instead of a real CLI tool.
- `wsprd` is invoked without `-f` (no dial frequency), so its frequency field is baseband-relative Hz, consistent with `jt9`/`decode_ft8` — absolute RF frequency (dial + offset) isn't computed anywhere yet.
- No cleanup/retention policy for processed WAV chunks in `chunks/` yet — they accumulate on disk indefinitely. (`DecodeWorker` no longer re-decodes them on a fresh start, but they still pile up and are never removed.)
- `jt9`/`wsprd` (the WSJT-X decoder) are still broken on the Pi specifically — missing runtime shared libraries (`Qt5Core`, `libgfortran`, `libgomp`) never vendored into the offline bundle (only their `-dev` build-time packages were). `ft8_lib`/`decode_ft8` works fine on the Pi and is what all real testing so far has used. `libfftw3f` (also on this list previously) is now vendored anyway as `csdr`'s runtime dep (`fftw-single-libs`), closing part of this gap for free.
