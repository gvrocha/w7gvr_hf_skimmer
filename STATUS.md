# STATUS.md

**Last updated:** 2026-09-24

## Where this stands right now

A real Pi 3B+ is now provisioned and running this project's software end-to-end for the first time. `deploy.sh`/`install.sh` were dry-run against it (a real gap was found and worked around, not yet fixed at the root — see Known gaps), and a genuine WAV chunk was captured from a real RTL-SDR Blog V4 for the first time, validating `build_rtl_fm_cmd()` against real hardware.
That same session surfaced a real architectural gap — `GpsClock` was never actually wired into `hsd.py`, so chunk timestamps relied on the Pi's own RTC-less (and, in practice, wrong) system clock — which is now fixed: `CaptureWorker` takes a pluggable time source, and `hsd.py` runs a `GpsClock` for the daemon's whole lifetime, falling back to system time only when `gpsd` is unreachable or hasn't got a fix yet.
GPS hardware itself is fully validated (see Track B-GPS, done). The Pi has since gotten a real 3D fix outdoors too, and a real 20m FT8 session there decoded 447 genuine over-the-air messages — but that same session found a real bug in `decode_worker.py` (every `ft8_lib`-decoded spot stamped at midnight), now fixed.
A follow-up session (moved the RTL-SDR + antenna to the dev Mac for faster iteration) found a **second, more consequential bug**: `rtl_fm` itself intermittently hard-clips its demodulated audio output even when the raw RF/ADC signal is completely clean and stable — likely the dominant reason decode yield has been inconsistent, more so than antenna/band conditions. See `hardware/20260920_rtl_fm_demod_bug.md` for the full investigation.
**That bug is now fixed in code** (2026-09-24): `rtl_fm` is replaced with an `rtl_sdr | csdr` pipeline (`vendor/csdr`, newly vendored) that does its own correct USB demodulation — validated twice against the same saved real 120-second I/Q capture (a from-scratch Python reference demod, and now the actual `csdr`-based fix cross-built for `linux-aarch64`), both decoding 130+ real messages cleanly with zero clipping, vs. `rtl_fm`'s mostly-empty output on the same signal. **Not yet live-tested against a real antenna** — no antenna access when this landed.
The remaining work before a reliable live station is live-testing this fix against a real antenna and getting an HF antenna permanently in place at the Pi's deployment location.

- [x] First real over-the-air FT8 decode, on the Pi (2026-09-11): with a real GPS fix acquired outdoors and a proper HF antenna connected, a 20m FT8 session (`14.074M`, `ft8_lib`) decoded **447 genuine messages** from real stations worldwide (Europe, Africa, the Americas) — first real proof the whole pipeline works end-to-end. Real gap found by inspecting the session log: `decode_ft8` (`ft8_lib`) always hardcodes `"000000"` as its own reported time-of-day, and `decode_worker.py` blindly trusted that field, so every `ft8_lib`-decoded spot was silently stamped at midnight regardless of when it was actually heard. Fixed: `decode_chunk()` now overrides every spot's `utc_timestamp` with `chunk_start()` (parsed from the chunk filename, which is authoritative — one chunk is always exactly one decode window) instead of trusting the decoder's self-reported time-of-day. Verified on the Pi against real captured chunks. Also added `tools/watch_decodes.py` (live decode monitor, groups output by decode window with a UTC-time + grid-square header) and `hardware/20260911_wifi_field_ops.md` (WiFi-AP connection instructions) for field use without the direct-cable Ethernet link.
- [x] Root-caused a second, likely more consequential decode-yield bug — this time in `rtl_fm` itself, not the antenna/band/RF chain (2026-09-20/21): moved the RTL-SDR + antenna to the dev Mac for faster iteration. A raw-I/Q gain sweep confirmed the ADC/tuner front end is clean up to ~42-43 dB (well above what caused saturation on the Pi at the same nominal gain, confirming that earlier issue was environmental, not this gain value). But a real decode test at that gain showed wildly inconsistent yield (0 decodes, then a lucky 90-second burst of 84, then 0 again) — traced to `rtl_fm`'s own demodulated *audio* output intermittently hard-clipping at the exact 16-bit ceiling, while a dedicated 120-second raw-I/Q capture over the same span proved the underlying RF signal stayed completely clean and stable throughout (0% clipping, steady power, every 15s block). Built an independent reference USB demodulator (`tools/reference_usb_demod.py`, numpy/scipy) against that same saved raw I/Q — it decoded **152 real messages, zero clipping, from all 8 chunks** — conclusively proving the bug is `rtl_fm`'s own processing, not the hardware, antenna, or band. Full writeup: `hardware/20260920_rtl_fm_demod_bug.md`.
- [x] Fixed the `rtl_fm` demod-clipping bug by replacing it with `csdr` (2026-09-24): investigated `csdr` (`jketterl/csdr`, actively maintained, used in OpenWebRX) as a lighter alternative to the numpy/scipy path — not packaged in Alpine, so vendored as a new git submodule (`vendor/csdr`) and cross-built for `linux-aarch64` the same way as `wsjtx`/`ft8_lib` (CMake; only new runtime deps are `fftw-single-libs` + `libsamplerate`, ~2.7MiB combined on Alpine, and `fftw-single-libs` incidentally is the exact library `jt9` is missing — see Known gaps). Confirmed the real cross-built `linux-aarch64` binary against the same saved 120s raw I/Q capture: **133 real messages decoded cleanly across all 7 chunks, zero clipping** — matching the earlier Python reference demod's result. Wired in for real: `capture_worker.build_csdr_capture_cmd()` builds an `rtl_sdr | csdr convert | csdr fractionaldecimator | csdr bandpass | csdr realpart | csdr limit | csdr convert` pipeline (csdr's own documented "modified Weaver demodulator" USB recipe), `CaptureWorker` now supports shell-pipeline `capture_cmd` (a `str`, run with `shell=True` in its own process group so `stop()` can tear down every stage together, not just the shell — a real termination bug that would otherwise orphan `rtl_sdr`/`csdr` processes), and `hsd.py`'s `start_listening()` uses the new builder by default. `build_rtl_fm_cmd()` is kept for reference, not deleted. 5 new tests (pipeline-string construction, shell-pipeline capture, and specifically that `stop()` kills every pipeline stage) — 49 passing total. **Not yet live-tested against a real antenna/`rtl_sdr`** — only validated by replaying the saved I/Q capture (`cat` substituted for the live `rtl_sdr` stage), since no antenna access was available when this landed. Two known limitations: no `vendor/csdr/build-darwin-arm64/` build (its upstream `CMakeLists.txt` shells out to `/proc/cpuinfo`, which doesn't exist on macOS — real Linux `aarch64`, the actual Pi target, is unaffected and was what got built and tested), and `csdr`'s own `CMakeLists.txt`/`LICENSE-GPL` declare it GPL-3.0-or-later (not the "mostly BSD" framing in its README) — worth a proper look before considering this settled, though using it as a separate CLI tool rather than linking its code is likely a non-issue.

## Known gaps / open questions

- `deploy.sh` assumes `rsync` is present on the remote Pi; it isn't shipped by minimal Alpine and isn't vendored into the offline bundle. Fix at the root next time: either vendor `rsync` into `provisioning/build-bundle.sh`'s package list, or make `deploy.sh` fall back to `tar`-over-SSH when `rsync` isn't found remotely.
- `gpsd-clients` (the standard `cgps`/`gpsmon`/`gpspipe` tools) isn't vendored into the offline bundle either — checked via `pkgs.alpinelinux.org`: only ~3.1MiB, and its only dependency (`libncursesw`) is already pulled in transitively by `python3`, so this is a cheap addition for the next bundle rebuild. Without it, watching satellite counts on the Pi needs a raw `socket`+`json` script against `gpsd`'s own protocol instead of a real CLI tool.
- `wsprd` is invoked without `-f` (no dial frequency), so its frequency field is baseband-relative Hz, consistent with `jt9`/`decode_ft8` — absolute RF frequency (dial + offset) isn't computed anywhere yet.
- No cleanup/retention policy for processed WAV chunks in `chunks/` yet — they accumulate on disk indefinitely.
- `jt9`/`wsprd` (the WSJT-X decoder) are still broken on the Pi specifically — missing runtime shared libraries (`libfftw3f`, `Qt5Core`, `libgfortran`, `libgomp`) never vendored into the offline bundle (only their `-dev` build-time packages were). `ft8_lib`/`decode_ft8` works fine on the Pi and is what all real testing so far has used. Note: `libfftw3f` is now vendored anyway as `csdr`'s runtime dep (`fftw-single-libs`) — `jt9`/`wsprd` would still need `Qt5Core`/`libgfortran`/`libgomp` added too, but this closes part of the gap for free.
